# Round 13 问题

每次只问一题。已定：segment/atom 是 fact 通道，默认 2 个位子，卡片是 AO 指针。未定：这 2 个位子从台账的哪一段里取。现在的实现是该 session 整本台账里按 BM25 取前 2，不看出没出过诊断或轨迹索引。

## 本轮用到的术语

- **AO pair**：台账的一行。action 是工具名和截短参数，observation 是确定性 synopsis。不是频道原文，也不是完整命令输出。
- **Atom**：没标成 segment 的 AO pair 进检索后的卡片。
- **Segment**：标了 `record_kind=segment` 的 AO pair，标出一次发送或接收把连续动作截开的边界。
- **轨迹索引（post_run view）**：session 提交后异步生成的冻结影响图。它带 coverage_manifest，写明覆盖了哪些 AO、省略了哪些区间。这不是诊断。
- **诊断**：按需构造 fork，或从轨迹索引派生失败诊断视图。多数 AO 永远不会成为 fork 锚点。
- **fact 配额**：一次因果检索里 segment/atom 的位子，默认 2。只在这一格内部排序，不能占 fork 或投影的位子。

❓ **Q129** - **fact 配额覆盖台账的哪一段**：频道消息是「这次发布必须蓝绿」。`ao-41` 的 synopsis 是「已 apply，蓝绿」。它落在最新轨迹索引的覆盖区间里，对应的 claim 是「写发布脚本 → 切流量」。`ao-90` 在该索引的省略区间里，synopsis 也提到蓝绿。`ao-120` 发生在索引水位之后，还在活会话里，synopsis 是「刚切到绿环境」。库里另有更早的 `ao-3`，synopsis 含蓝绿，索引没覆盖，但很旧。

- A. 这 2 个位子只从「最新轨迹索引没覆盖到的 AO」里取：省略区间，加上索引水位之后的活尾巴。其中按 BM25 取前 2。还没有轨迹索引的 session，整本台账都算没覆盖，仍按 BM25 取前 2，不改成只取时间上最近的两行。`ao-41` 已经在 claim 里，不再占 fact 位子。`ao-90` 和 `ao-120` 竞争这 2 席；`ao-3` 若 BM25 更高，仍可以留下。
- B. 只取时间上最近、且还没有 fork 锚点的 2 行，不看 BM25，也不看轨迹索引盖住了没有。哪怕最近两行与「蓝绿」无关，也占满 fact 位子。
- C. 整本台账都参与。BM25 最高的两行进入 fact 位子，即使 `ao-41` 已经有 claim 和 fork。

➡️ 推荐 A。这 2 个位子留给轨迹索引还没写成投影的事实。诊断本身很稀疏，用「还没有 fork」当过滤条件会把几乎整本台账都留在 fact 里。只取最近两行则会丢掉省略区间里更相关的 `ao-90`。

## 本轮新增术语（Q132）

- **influence**：相邻 block 之间的 InfluenceClaim。它表示上游把一个产物交到下游，并出现一个效果。例子：「写发布脚本」指向「切流量」，产物是发布步骤，效果是流量切到绿。它不是 skip，也不是 HypothesisBridge。
- **skip**：跨过覆盖清单里一段省略区间的 InfluenceClaim。它表示索引从这边跳到那边，中间的 AO 没有收进图。例子：ao-47…60 是「切流量」，ao-61…70 被省略，ao-71…75 是「看错误率」，则「切流量」→「看错误率」必须是 skip。它不是「这一步造成了那一步」。
- **邻域展开**：Memory Agent 用一张 claim 卡片的 id 调用的那一次。服务端只在这张卡片所属的冻结 view 里沿 InfluenceClaim 往外走，最多 12 个 block。走出来的路径只在这次返回里。诊断 agent 不用这个工具。
- **HypothesisBridge**：另一张图上的边，表示「这两个东西可能有关、尚未验证」。邻域展开不走它。
- **EvidenceBridge**：已通过验证门槛的桥。邻域展开也不走它。

❓ **Q132** - **展开时走不走 skip**（已定 B）：Memory Agent 对 `claim-card-17` 调用展开。这张卡片是 influence：「写发布脚本」（ao-41…46）→「切流量」（ao-47…60）。ao-61…70 在覆盖清单里被省略。下一条是 skip：「切流量」→「看错误率」（ao-71…75）。另有一条 skip 从「写发布脚本」跨过这段省略直达「看错误率」。

原题把「influence：切流量→看错误率」和「skip：写发布脚本跨过省略区间直达看错误率」并列。按校验，省略区间夹在切流量与看错误率之间时，切流量→看错误率本身必须是 skip。上面这句已按这个改过。答案 B 不变。

- A. influence 和 skip 都走。返回里既有跨过省略区间的 skip，也会走到「看错误率」。
- B. 只走 influence。skip 留在 view 上，展开不踩过去。从这张卡片出发停在「切流量」，不跨到「看错误率」。如果某一截只靠 skip 连着，展开就停在缺口这边。
- C. 只走和种子卡片同一种边。`claim-card-17` 是 influence，所以 skip 不走。若种子本身是 skip，则只走 skip，不走 influence。

➡️ 已定 B。skip 标记的是索引跳过的区间，不是 Memory Agent 要讲的影响链。

## 本轮新增术语（Q134）

- **诊断影响图（DIV）**：为这次失败另建的冻结 view，purpose=failure_diagnosis。它用来看错误怎么传，并给 fork 提供 grounding。它不是这次任务的 post_run 轨迹索引，也不代替那张索引。
- **失败路径**：DIV 里从相关动作走到坏结果的一串 influence claim，按顺序只保留产物和效果。skip 不算一步。例子：「发布步骤 → 流量切到绿环境」，接着「绿环境 → 错误率升高」。
- **子任务链**：在同一张冻结 view 里读时拼出来的 claim 路径。不另建一张图，也不铸造 subtask_id。
- **干预史**：某个 block、边或 cut 上已经接地的 fork 的反向索引。从历史路径上的边可以读到当时的决策，不会把这条 claim 改成已证实。

❓ **Q134** - **诊断按什么单位找历史**：这次发布切到绿之后错误率升高。诊断 agent 手里有两张图：本任务的 post_run 视图 `rev-deploy-2024`，以及针对这次失败的 DIV `div-error-2024`。DIV 里的失败路径是「发布步骤 → 流量切到绿环境」再「绿环境 → 错误率升高」。历史上另一次发布的 view `rev-rollback-2023` 里有同样顺序的两条 influence，并且 `rollback-choice@rev-1` 接地在第二条边上。那张历史 view 里还有无关的「写公告」block。

## 本轮新增术语（Q136）

- **整图分数**：一张历史 view 对当前 DIV 的一个总分。它只回答「这张图像不像」。它不指出里面哪一段在起作用。
- **分块分数**：这张 view 里每一个 block、每一条 claim 各自对当前 DIV 的分数。view 的总分由这些分块分数合成。
- **贡献片段**：分块分数过了门槛的那些 block 和 claim。没过门槛的留在原图里，不进这次返回。

❓ **Q136** - **写公告算不算贡献**：当前 DIV 的文字是「写发布脚本」「切流量」「流量切到绿环境」「错误率升高」。`rev-rollback-2023` 里「改发布脚本 → 开始切流」和这些词有重叠；「绿环境接流量 → 5xx 升高」用词不完全一样，意思接近；「公告稿 → 频道已发送」和切流、错误率没有共同的词。

- A. 只算整图分数。一个向量或一个总分表示整张 `rev-rollback-2023` 像这张 DIV。返回时要么整张都给，要么无法单凭这个分数把「写公告」摘出去。
- B. 每个 block、每条 claim 先各算一个对 DIV 的分数，整图分数是这些分数之和。过门槛的进返回。「公告稿 → 频道已发送」低于门槛，不进返回。整张图仍可以因为另外三条边分数高而排在前面。
- C. 分块算分，但门槛看词是否重叠。没有共同词的「写公告」直接丢掉。意思接近但用词不同的「5xx 升高」若没有共同词，也丢掉。

➡️ 推荐 B。这样「写公告没有抬高分」是它自己的分块分数低于门槛，不是从整图总分里猜的。用词不同但意思接近的「5xx 升高」仍可以靠向量留在贡献片段里。

## 本轮新增术语（Q137）

- **分块**：一个 block，或一条 claim。各自对当前 DIV 有一个分数。
- **子图**：同一张冻结 view 里，由 influence 边连在一起的若干 block 和 claim。跳过省略区间的 skip 不把两段连成一个子图。子图作为一个整体和当前 DIV 比一次。
- **连通**：两块之间有一条 influence claim。只出现在同一张 view 里、中间没有 influence 边，不算连在一起。

❓ **Q137** - **相似分落在单块上还是子图上**：`rev-rollback-2023` 里三条切流边首尾相连：「改发布脚本 → 开始切流」「切流 → 绿环境接流量」「绿环境接流量 → 5xx 升高」。`b-notice`「公告稿 → 频道已发送」没有 influence 边连到这条链上。当前 DIV 是两条边：「发布步骤 → 流量切到绿环境」「绿环境 → 错误率升高」。用词和条数都对不上。

- A. 不切子图。三条切流边和「写公告」各自对 DIV 打分。view 的名次是这些分数之和。三条边不会合成一个结构去比。
- B. 按 influence 连通切成子图。那三条切流边是一个子图，对 DIV 打一个分，不要求和 DIV 的两条边逐条对齐。「写公告」是另一个子图，分数低，不进返回。若「写公告」被一条 influence 边串进切流链，它会留在那个子图里，这次摘不掉。
- C. 不拆开。整张 `rev-rollback-2023` 一个分数，命中后整张返回，「写公告」也在。

➡️ 推荐 B。诊断要找的是「切流然后出错」这一小段结构，不是散落的单词，也不是整次发布里的公告。这个例子里写公告没有 influence 边连上来，所以它单独成图，排不进这次结果。

## 本轮新增术语（Q138）

- **子任务划分**：提取一张冻结 view 时，把 block 收进事先已有名字的子目标。一个子目标里的 block 和它们之间的 influence 边构成一个检索用子图。
- **子任务身份**：会累积引用和效用的 subtask_id。这里不新造这种身份。效用仍记在 fork 和 task_id 上。
- **剩余片段**：计划里没有对应子目标的动作。例如计划只写了「切流」，却做了「写公告」。

❓ **Q138** - **子图边界从哪来**：`rev-rollback-2023` 这一次任务的计划写了两个子目标：「切流」和「通知」。「写发布脚本」「切到绿」「看错误率」收进「切流」。「写公告」「发到频道」收进「通知」。检索时这两个子图各自和当前 DIV 比，不要求边逐条对齐。

- A. 边界来自跑任务之前已经写下的子目标。提取时按这些名字收 block。没被任何子目标收进的动作放进剩余片段，不和「切流」混在一个子图里。子图只用于排序，不铸造 subtask_id。
- B. 跑任务之前没有这份名单。提取影响图的模型自己把动作切成「切流」和「通知」，写进冻结 view，之后按这个切分排序。
- C. 提取时不划分子图。子目标只在读取时沿 claim 拼成路径。检索仍按整张 view，或按单个 block、单条 claim。

➡️ 推荐 A。子目标的名字在跑之前就有，提取只是把 block 收进去。模型现切会把一次发布里临时写的公告定成一个长期用来检索的类别。剩余片段单独放，是为了不让没写进计划的动作混进「切流」的相似分。

➡️ 推荐 C。参与者是 block 上本来就有的字段。模型现起的子任务名字没有一份名单可以核对。同一 agent 内部不再往下拆。

- **旁路子图**：同一张 DIV 里的其他检索子图。例子：含「写公告」的「通知」子图。

❓ **Q140** - **诊断用哪个子图当查询**：当前 DIV `div-error-2024` 被模型划成两个子图。「切流」里是写发布脚本、切到绿、错误率升高。「通知」里是写公告。历史 view `rev-rollback-2023` 也被划成同样的两个子图。`rollback-choice@rev-1` 接地在历史「切流」子图里「5xx 升高」那条边上。边的措辞不必对齐。

- C. 只有失败子图去查。查询是「切流」这一段。命中是历史的「切流」子图，以及接地在该子图里的 `rollback-choice@rev-1`。历史的「通知」子图不返回。

➡️ 推荐 C。这次诊断要找的是切流之后出错、以及当时的决策。公告子图留在原图里，不因同一次任务被一起查出来。

## 本轮新增术语（Q142）

- **结论块**：DIV 上角色为 conclusion 的那个 block，表示这张图要解释的失败结果。例子：「错误率升高」。它在建 DIV 时就在图上，不是检索那一步才写出来的。
- **失败子图**：已经抽好的检索子图里，含有这个结论块的那一个。例子：「切流」子图含「错误率升高」，「通知」子图不含。

❓ **Q142** - **谁选定失败子图、谁发起检索**：`div-error-2024` 的结论块是 `b-rate`「错误率升高」，落在模型已经划好的「切流」子图里。「通知」子图里没有结论块。历史「切流」子图里有 `rollback-choice@rev-1`。

- A. 规则选定，规则发起。含结论块的「切流」就是失败子图。DIV 一冻结，服务端用它去查历史子图。诊断 agent 不判断哪个是坏结果，也不调用这次检索。它直接读到历史「切流」和 `rollback-choice@rev-1`。
- B. 规则选定，诊断 agent 发起。失败子图仍是含 `b-rate` 的「切流」。诊断 agent 只能用这个子图去查，不能改查「通知」。它可以不调用。
- C. 诊断 agent 既选定又发起。它看着已抽好的子图，自己判断「切流」是坏结果并发起检索。它若把「通知」判成坏结果，查询就变成「通知」。

➡️ 推荐 B。坏结果是建 DIV 时已经落在结论块上的失败，不在检索时再判一次。调用本身由诊断 agent 发出，所以它看过子图之后可以不查。它不能把查询改到没有结论块的「通知」上。

## Q142 已定：B

## 本轮新增术语（Q143）

- **一次调用**：诊断 agent 拿失败子图发起的那一次子图检索。
- **历史命中**：一份历史检索子图，加上接地在这份子图里面的 fork。同一张历史 view 里的旁路子图不在这份命中里。

❓ **Q143** - **一次调用返回几份历史子图**：诊断 agent 用 `div-error-2024` 的「切流」去查。库里有三份历史子图都像切流后出错。第一份在 `rev-rollback-2023`，接地 `rollback-choice@rev-1`。第二份在 `rev-canary-2022`，接地另一个 fork。第三份在 `rev-old-2021`，没有 fork。这三张 view 里各自还有「通知」子图。已定的诊断参照路径最多 3 条。

- A. 只返回分数最高的那一份：`rev-rollback-2023` 的「切流」和 `rollback-choice@rev-1`。第二份、第三份不返回。
- B. 最多返回 3 份，按模糊相似排序。每份是该历史子图加上接地在其中的 fork。子图里的 block 仍不超过 12 个。三张 view 里的「通知」都不返回。库里不足 3 份时有几份返回几份，不用别的子图补满。
- C. 不设份数上限。过了相似门槛的历史子图全部返回。

➡️ 推荐 B。诊断要对照的是少数几次同类失败，不是只看最高的一次，也不是把所有擦边的历史子图都放进上下文。3 份和已定的参照路径上限一致。

## Q143 已定：B

## 本轮新增术语（Q144）

- **诊断子图命中**：一次失败子图检索返回的一份结果。里面有一份历史检索子图，加上影响定位落在该子图里的 fork。它不是整张历史 view，也不包括同一张 view 里的旁路子图。
- **影响定位（接地）**：一份 fork 修订指向冻结 view 上的一个位置，位置是某个 block、某条边或某个 cut。fork 不是影响图里的 block。例子：`rollback-choice@rev-1` 指在「绿环境接流量 → 5xx 升高」这条边上。
- **七段快照**：这份 fork 上的七段文字：session_title、current_state、task_and_goals、key_facts_and_decisions、files_and_context、errors_and_corrections、open_issues。它不是 AO 原文。`key_facts_and_decisions` 里可以写「错误率升高就切回蓝」。
- **分支动作摘要**：这份 fork 的某个分支做了什么的短述。例子：`br-observed` 是「切回蓝环境」。它不是 guidance 全文。
- **Guidance**：写在分支上的指导文字，随分支保存。它不在七段快照里，也不等于分支动作摘要。
- **原始 AO**：台账里被这份 fork 引用的动作原文。因果上下文是这些 AO 的引用名单，不是七段正文。

❓ **Q144** - **命中里的 fork 带多少文字**：历史「切流」子图被返回。`rollback-choice@rev-1` 的影响定位指在该子图的边「绿环境接流量 → 5xx 升高」上。七段里写着「错误率升高就切回蓝」。分支 `br-observed` 是「切回蓝环境」。另有 guidance 和原始 AO。

- A. 命中里这个 fork 只有 `rollback-choice` 和 `rev-1`。七段文字要另一次读取才看得到。
- B. 命中里带上七段快照，以及 `br-observed` 的动作摘要「切回蓝环境」。不带 guidance 全文，不带原始 AO。子图本身仍在这份命中里。
- C. 命中里带上这份 fork 的全部内容：七段、guidance、因果上下文里的 AO 原文。

➡️ 推荐 B。诊断 agent 要读的是当时的决策「切回蓝」。只给 id 时它还要再读一次。guidance 和原始 AO 仍留在后面的读取里。

## 本轮新增术语（Q145）

- **一任务多 Fork**：一个任务里可以有多份 fork，每份接地在自己的失败位置上，各自有完整分支。不另造一个「根因集合」把它们收成一个对象。
- **cause_set**：把多份根因收成一个节点字段或一个集合对象。已定不做这个。
- **Memory Hint**：Memory Agent 发给任务 agent 的一条提示。一条 Hint 可以引用多份 fork。它不是检索结果本身。

❓ **Q145** - **两个失败子任务的 fork 何时一起出现**：总任务是发布。子任务「切流」失败，`fork-cutover` 接地在切流子图上，意见是切回蓝。子任务「迁移」失败，`fork-migrate` 接地在迁移子图上，意见是先修 schema。总任务要两份都成功。第二次再跑这次发布。

- A. 维持现在。诊断只查含唯一结论块的那一个子图。两份 fork 各自按文本单独被检索，同一次结果不保证都在。Hint 只有在两份已经都出现在检索结果里时，才能写进同一条。
- B. 一个子图里有自己的失败结论，就各算一个失败子图，诊断 agent 对每一个都发起一次检索。第二次跑总任务时，同一次结果带回 `fork-cutover` 和 `fork-migrate`。这次只执行迁移时，只带回 `fork-migrate`。不造 cause_set。
- C. 两份 fork 收成一个组。无论这次在跑总任务还是只跑迁移，检索到其中一份，另一份都附在同一次结果里。

➡️ 推荐 B。两份修复要在再跑总任务时一起出现，但只碰其中一个子任务时不必把另一份拖进来。它们仍是两份 fork，不收成一个根因集合。

## Q145 已澄清

不需要把两份 fork 绑在同一次结果里。两次检索各命中一份即可。

## 本轮新增术语（Q146）

- **fork-cutover / fork-migrate**：两份普通 fork 的例子名字。一份接地在切流失败上，一份接地在迁移失败上。不是新的 fork 种类，系统里不必存在这两个类型名。
- **分两次检索**：第一次查询带回切流那份 fork，另一次查询带回迁移那份 fork。两次不必是同一次调用，也不必绑成一组。

❓ **Q146** - **第二份 fork 要不要被诊断写出来**：发布里切流和迁移都失败了。切流子图的结论是「错误率升高」，迁移子图的结论是「schema 不匹配」。按已定规则，只有含那一个 DIV 结论块的子图会发起诊断检索。若结论块只落在切流上，迁移这份 fork 不会在诊断里被写出来。

- A. 每个带自己失败结论的子图都由诊断 agent 各发起一次检索，各写一份 fork。之后切流那次检索命中切流的 fork，迁移那次检索命中迁移的 fork。两次不必绑在同一次结果里。
- B. 维持一个失败子图。只写切流那份 fork。迁移这份没有被诊断写出来，以后的检索也找不到它。
- C. 两份失败都写进同一份 fork。一次检索就把切流和迁移的意见一起带回。

➡️ 推荐 A。分两次检索要成立，两份 fork 都得先存在。它们仍是两份普通 fork，不收成一组，也不合成一份。

## Q146 已定：A

每个带自己失败结论的子图各写一份 fork。

## 本轮新增术语（Q147）

- **任务级结论**：整张 DIV 上那一个结论块，例如「发布失败」。它表示总任务没完成。
- **子图失败结论**：某个检索子图内部写出的失败，例如切流子图里的「错误率升高」，迁移子图里的「schema 不匹配」。通知子图里的「公告已发送」不是失败。

❓ **Q147** - **怎样算这个子图自己的失败结论**：发布的 DIV 上有一个任务级结论块「发布失败」。「切流」子图里有「错误率升高」。「迁移」子图里有「schema 不匹配」。「通知」子图里是「公告已发送」。

- A. 子图里出现失败结果，就有自己的失败结论。切流、迁移各发起一次诊断检索，各写一份 fork。通知不发起。「发布失败」这个总结论不再单独发起第三次。
- B. 只有含角色为 conclusion 的块才算。若整张 DIV 只有「发布失败」这一个结论块，就只有含它的那个子图发起检索。迁移不会写 fork，除非提取时把「schema 不匹配」也标成 conclusion。
- C. 诊断 agent 自己圈定哪些子图算失败。图上的「错误率升高」和「schema 不匹配」不会自动各发起一次检索。

➡️ 推荐 A。两份 fork 要各自能被检索到，失败得落在各自的子图上。总任务的「发布失败」只说明没完成，不代替切流和迁移各自的失败。通知没有失败结果，不写 fork。

## Q147 已定：A

子图内的失败结果就是该子图的失败结论。任务级总结论不单独再查。

## 本轮新增术语（Q148）

- **失败标记**：提取子图时写在某个结果上的标记，表示这是失败，不是成功。例如「错误率升高」「schema 不匹配」带标记，「公告已发送」不带。
- **提取模型**：划定检索子图的那一个模型。它在提取时看得到动作和结果。

❓ **Q148** - **失败标记谁来写**：「切流」里有「错误率升高」，「迁移」里有「schema 不匹配」，「通知」里是「公告已发送」。任务级结论块仍是「发布失败」。有失败标记的子图才各发起一次诊断检索。

- A. 提取模型在写入子图时加上失败标记。诊断 agent 不改这些标记，只对带标记的子图发起检索。公告没有标记，不写 fork。「发布失败」不再额外加一次。
- B. 不写标记。诊断 agent 阅读子图文字，自己判断「错误率升高」和「schema 不匹配」是失败，再决定是否发起检索。
- C. 只有角色为 conclusion 的块算失败标记。子图里的「错误率升高」若没有这个角色，就不算。

➡️ 推荐 A。失败结果在提取时就已经能看出来，标记和子图一起写入。诊断 agent 按标记发起检索，不再把「算不算失败」重判一遍。

## Q148 已定：A

失败标记由提取模型写入。诊断 agent 不改标记。

## 本轮新增术语（Q149）

- **诊断检索**：失败子图去比历史子图，用来写出这一次的 fork。发生在失败已经进入 DIV 之后。
- **再次运行时的检索**：下一次跑发布时去找已经写好的 fork。此时这一次的子图可能还没提取出来。

❓ **Q149** - **再次运行时怎样打中那份 fork**：切流和迁移的 fork 已经写好。七段里分别有「错误率升高就切回蓝」和「先修 schema」。第二次跑发布，先碰到切流，后碰到迁移。这一次的子图还没提取。

- A. 仍用子图对子图。第二次运行要等这一次的「切流」子图提取出来，才能去命中上次的 fork。迁移同理。子图还没提取时，fork 不会被这次查询打中。
- B. 再次运行用普通的 fork 检索。查询文字打在 fork 的七段快照上。谈到切流的那一次命中切流的 fork，之后谈到迁移的那一次命中迁移的 fork。不依赖这一次的子图已经提取。
- C. 第二次运行开始时，一条 Memory Hint 同时带上两份 fork。运行途中不必再检索。

➡️ 推荐 B。再次运行要在子图提取之前就用上 fork。两次查询各打中一份，和已经定下的「分两次检索」一致。诊断检索仍负责在失败之后写出 fork，不代替运行途中的这次查找。

## Q149-B 不成立

一般情况是另一个任务。旧 fork 七段里的原话对不上新任务的措辞。

## 本轮新增术语（Q150）

- **历史失败子图**：上一个任务里已经写好、带失败标记的检索子图，上面接地着一份 fork。例子：发布任务里的「切流」子图，fork 的七段是「错误率升高就切回蓝」。
- **当前步骤**：另一个任务进行到某一步时的查询，用词可以和历史子图不同。例子：结算服务上线里的「把流量拨到新集群」。
- **模糊相似**：比较的是意思，不是七段原文里的同一句话。纯 BM25 只看词是否重叠，对不上「切回蓝」和「拨到新集群」。这里要用已定的混合档，在有真实向量时把向量算进去。

❓ **Q150** - **另一个任务怎样分两次打中两份 fork**：发布任务留下两份 fork。一份在「切流」子图上，七段是「错误率升高就切回蓝」。一份在「迁移」子图上，七段是「先修 schema」。新任务是结算服务上线，进行中，它自己的子图还没提取。先遇到「把流量拨到新集群」，后遇到「导入结算表」。用词和旧的七段不一样。两次检索各带回一份即可。

- A. 等新任务的子图提取出来，再用子图对子图。提取之前，「把流量拨到新集群」打不中旧的切流 fork。
- B. 不等新任务的子图。当前步骤对历史失败子图做模糊相似。「把流量拨到新集群」打中旧的切流子图，带回接地的那份 fork。之后「导入结算表」打中旧的迁移子图，带回另一份。不拿旧 fork 的七段原文当查询条件。
- C. 先要有一条已验证相似边连到旧 fork。结算服务第一次跑的时候还没有这条边，所以打不中。要等以后的诊断判定相似之后，下一次才能检索到。

➡️ 推荐 B。另一个任务在进行中就要用上旧 fork，不能等自己的子图提取完，也不能等一条相似边先被写好。两次查询各打中一份历史失败子图，fork 跟着该子图回来。

## Q150 已定：A

诊断等子图提取完成后再子图对子图。

## 本轮新增术语（Q151）

- **轨迹提交**：一次任务运行 commit 之后。post_run 影响图在这之后由异步索引服务提取，不在任务进行中提取。
- **进行中的频道消息**：Memory Agent 在子图提取之前就能看到的那句话。例子：结算服务上线时的「把流量拨到新集群」。

❓ **Q151** - **Memory Agent 在子图提取前检索什么**：结算服务还在进行，自己的子图还没有。频道里出现「把流量拨到新集群」。发布任务的「切流」子图早已提取，上面接地着「切回蓝」那份 fork。诊断要等结算服务的子图提取完才做子图对子图。

- A. Memory Agent 这时不检索 fork，也不检索影响图。旧的切流 fork 要等诊断做完子图对子图才出现。这条频道消息打不中它。
- B. Memory Agent 不等当前子图。它用这条频道消息，对已经提取好的历史失败子图做模糊相似，命中旧的切流子图和接地的 fork。诊断仍按 A，等本任务子图提取后再做子图对子图。
- C. Memory Agent 维持卡片检索：fork 的七段原文，加上 block/claim 投影，按词重叠排序。「把流量拨到新集群」和「切回蓝」没有共同的词，打不中。不做子图对子图。

➡️ 推荐 B。进行中还没有本任务的子图，诊断可以等，Memory Agent 正在看的就是这条频道消息。它拿这句话去比已经提取好的历史失败子图，fork 跟着子图回来。

## Q151 已接替

Memory Agent 有一个子图提取工具，自己决定何时调用。提取完成后再做子图检索。

## 本轮新增术语（Q152）

- **AO**：台账的一行，是工具名、截短参数和一段确定性 synopsis。它不是频道原文，也不是完整命令输出。例子：结算服务执行到「把流量拨到新集群」时的那一行。
- **进行中提取**：commit 之前，Memory Agent 调用子图提取工具，只用到目前为止的 AO 划检索子图。它不是 commit 之后那次 post_run 提取。结算服务这时只做到「把流量拨到新集群」，后面的「导入结算表」还不在账本里。
- **冻结索引**：commit 之后由异步索引服务留下的 post_run 视图，以及写在上面的检索子图。以后的诊断可以把它当历史子图来查。进行中还没 commit 的半截动作不在这里面。例子：发布任务已经 commit，它的「切流」子图在冻结索引里。
- **post_run 提取**：轨迹提交之后的那一次影响图提取。它写成冻结索引。Memory 的进行中提取不代替它。
- **查询子图**：只为这一次子图检索现切出来的子图。用它去比已经在冻结索引里的历史子图，这次用完不进入冻结索引。它不是会留下、被别的任务再查到的历史子图。
- **影响定位**：一份 fork 指向冻结视图上的一个 block、一条边或一个 cut。fork 本身不是影响图里的 block。例子：「切回蓝」那份 fork 指在历史「切流」子图的一条边上。

❓ **Q152** - **进行中提取的子图写不写进冻结索引**：结算服务还在进行。Memory Agent 判断该提取了，工具读到目前的 AO，划出「拨到新集群」这个子图。历史的「切流」子图已经在冻结索引里，上面有「切回蓝」的 fork。commit 之后仍会做一次 post_run 提取。

- A. 进行中提取只产出查询子图，不写入冻结索引。用它去比历史「切流」，带回接地的 fork。这次半成品不留给以后的任务当历史子图。commit 后的 post_run 仍照常写入。
- B. 进行中提取写入冻结索引，立刻成为可被检索的历史子图。commit 后的 post_run 再取代它。在被取代之前，别的任务能检索到这个还没做完的「拨到新集群」。
- C. 工具在 commit 之前不能提取。Memory Agent 只能等轨迹提交。进行中的「把流量拨到新集群」不能触发子图检索。

➡️ 推荐 A。进行中的账本还不是一次完整任务。查询子图够用来打中旧的切流 fork。把它写进冻结索引，会让没做完的步骤被后来的任务当成历史失败子图。commit 之后的那次提取才留下。

## Q152 已定：取消进行中提取

不取上面的 A/B/C。子图只由 commit 之后的提取产生。Memory Agent 不持有子图提取工具。Q151 被取代。
