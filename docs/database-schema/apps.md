# App registry

The app registry (`apps/web/src/server/apps/`) holds the third-party apps Workspaces register. Each
is an OpenID Connect client of CoForge's authorization server, its key the `client_id`. There is no
marketplace: a registered app is installed only in the Workspace that registered it. Migrations
`20261020120000_app_registry`, `20261020130000_app_category_identity_scope` (the category, the
`identity` scope, and no resource URI), `20261020140000_app_homepage_optional` (an app needs only a
name), `20261021120000_app_logo` (its uploaded logo) `20261021180000_app_data_permissions` (the
data it may read where it is installed) and `20261022120000_app_installation_setup` (the page it is set
up on after installation).

The built-in Agent Apps (`system.reminder`, `system.cleaner`) are not rows. They are the SDK's
`BUILT_IN_APPS` (`packages/coforge-sdk/src/internal/app-config.ts`), run by the daemon, and
`agent_app_configs.appId` names one of them with no foreign key.

`apps` — one row per registered app:

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | UUIDv7 primary key, generated by the Prisma client. |
| `key` | TEXT | Unique, `^[a-z][a-z0-9-]{2,63}$`, set at registration and never changed: the one given, or, when none is, the name's slug and a random six-character suffix (tried again with a new suffix when taken). Never dotted, so never a built-in app's key. It is the `client_id`, and the audience of the tokens Agents get for the app. |
| `ownerWorkspaceId` | UUID | The registering Workspace, cascade delete. |
| `name` | TEXT | 1 to 80 characters, trimmed; no control or bidirectional characters, not only invisible ones. |
| `description` | TEXT | At most 500 characters; line breaks, but no other control or bidirectional characters. |
| `whenToUse` | TEXT | At most 160 characters on one line, shown to Agents; no control or bidirectional characters. |
| `homepageUrl` | TEXT | Absolute https URL; null when the app gives none. |
| `redirectUris` | TEXT[] | None to 10 (an app with none signs no one in; its Agents can still get tokens), none twice, matched as exact strings (RFC 9700): https, or http on `localhost`, `127.0.0.1` or `[::1]`, no fragment. |
| `category` | TEXT | `ai-automation`, `communication`, `productivity`, `developer-tools`, `data-analytics`, `business-ops`, `infrastructure`, `content-creative` or `other` (the default), enforced by `apps_category_check`. |
| `allowedScopes` | TEXT[] | Always `openid`, `profile` and `identity`, and `email` when the app may ask for it; nothing else. |
| `logoObjectKey` | TEXT | The uploaded logo's object in the image store (`workspaces/<ownerWorkspaceId>/apps/<key>/logos/<uuid>/original`); null shows the monogram made from the name. Bytes never live in PostgreSQL. |
| `logoContentType` | TEXT | The logo's checked type (`image/jpeg`, `image/png`, `image/gif` or `image/webp`), served with its bytes; set and cleared with `logoObjectKey`. |
| `clientSecretHash` | TEXT | SHA-256 (hex) of the client secret `cfa_secret_…`, whose plaintext is returned once at registration or rotation. |
| `secretRotatedAt` | TIMESTAMP(3) | Last rotation. |
| `permissionGroups` | TEXT[] | The data the app declares it reads where it is installed: any of `workspace`, `agent`, `channel` and `computer`, each read-only, once each (`apps_permission_groups_check` only limits the values to those four; the application keeps them in that order); empty by default. Separate from `allowedScopes`. |
| `permissionRevision` | INTEGER | 0 at first, one more each time `permissionGroups` changes (saving the same set leaves it). |
| `setupUrl` | TEXT | The page an owner or admin continues setup on after installing; null when the app needs no setup. https, or http on `localhost`, `127.0.0.1` or `[::1]`; at most 2000 characters, canonical, no user info or fragment (`apps_setup_url_check` checks the length, the fragment and the scheme; the application checks the rest). |
| `setupDescription` | TEXT | One line saying what the setup page is for; at most 500 characters (`apps_setup_description_check`); empty by default. |
| `setupRevision` | INTEGER | 0 at first, one more each time `setupUrl` changes, setup turned on or off included; a change of `setupDescription` leaves it (`apps_setup_revision_check`). |
| `createdByUserId` | UUID | Set null when the User is deleted. |
| `createdAt`, `updatedAt` | TIMESTAMP(3) | |

Every URL column holds a URL in its canonical form, the string a WHATWG URL parser writes back
(`new URL(s).href === s`), with no user name or password: what is stored is what is compared and
shown. A non-canonical spelling is refused, not rewritten (`https:evil.example/cb`,
`http://0x7f.1/cb`, `https://ACME.example/`), so a bare origin is written with its slash:
`https://acme.example/`.

An app's logo is set, replaced and reset by its Workspace's owners and admins, as an Agent's avatar
is: the same image store and checks (at most 5 MB, bytes sniffed), but a GIF (`GIF87a`/`GIF89a`)
is taken too, as Raft takes one (`APP_LOGO_UPLOAD_TYPES`; avatars and icons still refuse it); the old
object removed on a replace, a reset or the app's delete (the key the deleted row had, so a logo
uploaded meanwhile goes too). Settings sets and resets it through the `uploadWorkspaceAppLogo`
(FormData) and `resetWorkspaceAppLogo` Server Functions. Surfaces show `appLogoUrl`: the image CDN
at the icon size when the deployment has one (its bucket must allow the logo key shape first:
[profile image domain](../operations/aliyun-oss-cdn/profile-image-domain.md)), otherwise the GET
route `/api/workspaces/<ownerWorkspaceId>/apps/<key>/logo`, which serves people of a Workspace where
the app is installed. The consent page shows the logo; the page for a person with no such Workspace
does not. A logo that does not load falls back to the monogram.

`app_installations` — an app installed in a Workspace: `appId` (cascade), `workspaceId` (cascade),
`installedByUserId` (set null), `approvedGroups` (TEXT[], empty by default;
`app_installations_approved_groups_check` limits the values to the four groups, the application keeps
their order), `approvedRevision` (INTEGER, 0 before any approval), `approvedAt`, `approvedByUserId` (set null when the User is deleted), `setupCompletedRevision` (INTEGER, null until the app reports setup done) and `setupCompletedAt` (TIMESTAMP(3); null exactly when the revision is: `app_installations_setup_completion_check`), `agentAccess` (TEXT, `all` by default or `selected`; `app_installations_agent_access_check`), `createdAt`, unique (`appId`,
`workspaceId`). Today only the registering Workspace installs its app; the table is where a later
install elsewhere goes. A Workspace's delete removes its apps and installations.

`app_installation_agents` — the Agents selected for an installation (migration
`20261023140000_app_installation_agent_access`): `installationId` (cascade) and `agentId` (cascade,
so deleting an Agent removes its row), primary key both. The rows count only while the installation's
`agentAccess` is `selected` and stay, unused, under `all`.

## Agent access scope

An installation's `agentAccess` says which Agents may use the app: `all` (the default, every Agent in
the Workspace, later ones included) or `selected` (only the Agents in `app_installation_agents`).
All Agents is Raft's behaviour; Selected Agents is a CoForge extension beyond Raft, which has no
per-Agent install scope. Owned by `apps/web/src/server/app-agent-access/` (`InstallationAgentScope`);
the rule is [Agents' app access](app-agent-access.md).

- Owners and admins (`manageApps`) change it in the app editor and the app detail; the change applies
  at once, on its own Server Function, and the last write wins (no revision guard). Members read the
  mode and the number of Agents. Registering an app starts at `all`, with no selection.
- Switching revokes no grant. Selecting an Agent that is not a live Agent of the Workspace that is neither a system Agent (the per-member assistants) nor the Workspace Memory Agent (it gets no Apps section) is refused.

## Data permissions

Behind the `app-data-permissions` feature flag ([feature flags](../feature-flags.md)), owned by
`apps/web/src/server/app-permissions/`. The registering Workspace's owners and admins declare the
app's `permissionGroups` in its editor; an owner or admin of a Workspace where it is installed
approves them there. An approval sends the `permissionRevision` it was shown and records that
revision, the groups declared at it, who approved and when; a revision that is no longer current is
refused (`CONFLICT`, `app-permissions-changed`). Registering may declare groups too, in the same
transaction as the registration (`AppEditorSave.register`); the registering Workspace's installation
then starts with them pending, since registering is not an approval (Raft's registration-time
approval is unverified, so the approval stays a separate act).

Deliberate departures from Raft: the groups are four read-only checkboxes (Raft: a Resource | Access table of five rows, the fifth, agent reminders, writable); the reminders write group is not offered until a product decision. Approval happens on the installation card in the app editor, because apps are private to their Workspace (Raft: the installed-app detail or the marketplace install modal). No Suspended or App disabled installation state exists. Members see the summary on the app card and can open a read-only app detail (every role can: description, homepage, Login with CoForge scopes, setup status, what it reads and any pending update; Continue/Manage, Approve update and the installation ID are for owners and admins).

- Effective groups, what the app may read in that Workspace: `approvedGroups` ∩ `permissionGroups`.
- Pending groups, waiting for approval: `permissionGroups` not in `approvedGroups`.
- A declaration that drops a group takes effect at once, with no approval, and removes the group from
  every installation's `approvedGroups` in the same transaction, so declaring it again is pending
  until approved again.
- The editor's Save writes the profile fields and the declaration in one transaction: a refused field
  leaves the declaration, its revision and the approvals as they were.
- While the flag is off for a Workspace, its members see none of this, declaring and approving are
  refused (`ACCESS_DENIED`, `app-data-permissions-off`), and saving an app leaves these columns as
  they are.

## Installation setup

Behind the `app-installation-setup` feature flag, owned by `apps/web/src/server/app-installation-setup/`;
the API an app calls is [installation setup](../authorization-server/app-installation-setup.md). The
registering Workspace's owners and admins declare the page and what it is for in the app's editor; the
app reports, per installation, that it finished a revision.

- Status, derived and never stored: no `setupUrl` is `not_required`; `setupCompletedRevision` equal to
  the app's `setupRevision` is `complete`; anything else is `pending`.
- The revision goes up in the same SQL statement that writes the URL, only when the URL differs from the
  stored one. Changing the page, or turning setup off and on, therefore asks every installation again;
  changing only the description keeps a finished setup finished.
- Completion belongs to one installation, so a new installation of the app starts `pending`.
- The editor's Save, and a registration, write the setup with the profile and the permissions in one transaction. While the
  flag is off for a Workspace its members see none of this, declaring is refused (`ACCESS_DENIED`,
  `app-installation-setup-off`), and saving an app leaves these columns as they are.
