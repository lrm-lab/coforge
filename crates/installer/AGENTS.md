# coforge-installer instructions
These rules extend the repository root `AGENTS.md` for `crates/installer/`, the Rust
crate that builds `coforge-installer`. The root architecture invariants state the installer's
ownership; this file holds how it controls a running Computer, its commands,
toolchain, and gotchas.
## Module map
The module map is in [`src/AGENTS.md`](src/AGENTS.md), next to the modules it describes.
## Contract with the product
- Every change to an installation belongs to this crate: install, upgrade, repair, status, and
  recover, with the machine mutation lock, download and verification, activation, service control,
  probe, rolling back a failed upgrade, and receipts. The toolchain is pinned in
  `crates/installer/mise.toml`; this crate has its own version and release. Move that logic out of
  `packages/computer`; never add more of it to Computer.
- Computer fetches the installer fresh from the release feed's `installer/latest` for each operation, launches it, and reads its receipt, so an installer fix applies to the next upgrade without a Computer release. The installer reads a Computer's state only through `coforge-computer __lifecycle` (versioned JSON), never the local protobuf RPC, and stops and starts it through the OS service manager; an installer upgrade does not pause or drain busy Agents first.
- `contract/` is generated by `packages/computer`, the source of truth:
  `bun run --cwd packages/computer generate:installer-contract` writes a JSON
  Schema (draft 2020-12) per JSON shape and a golden instance of every file.
  Never edit it by hand; change the TypeScript owner and regenerate. The
  generator lists which module owns each file.
- The Rust tests read every golden, round-trip it, and add an unknown field to
  prove it is ignored. Keep contract structs free of `deny_unknown_fields`, and
  mirror optional TypeScript fields with `skip_serializing_if`.
- Anything the installer writes (receipts, `active.json`, and a whole `versions/<v>`
  directory per release target) is emitted by the tests into `contract/rust/`,
  which `packages/computer/test/installer-contract.test.ts` reads with the zod
  schemas and the product's own readers (the version directories go through
  `ComputerUpdater`'s offline verification). `cargo test` rewrites those files;
  commit them.
- The version directories go in one JSON file, `contract/rust/installed-versions.json`,
  never as raw files: CRLF launchers fail `git diff --check` (CI's Plan checks).
- CI regenerates both sides and fails on any difference: the Computer job
  after `generate:installer-contract`, this crate's native entries after
  `cargo test`. `contract/.gitattributes` turns off line-ending conversion so
  the files match byte for byte on Windows too.
- Receipts: `InstallerReceiptSchema` and `INSTALLER_EXIT_CODE` state the rules (exit codes, also
  without a receipt; replay; 64 KiB); `contract/receipt-cases.json` lists what it accepts and
  refuses, and `cargo test` writes each allowed row to `contract/rust/`.
- A receipt's `errorCode` is one of the SDK's (`contract/upgrade-error-codes.json`), or none;
  never add an installer-only code.
- `paths.rs` must equal Bun's `node:path` byte for byte; tests compare `to_str()`,
  never `PathBuf`, which equates by component.
## Command line
- `coforge-installer install --version <latest|X.Y.Z> [--from-directory <dir>]`: the first install.
  The same transaction as `upgrade`, with a generated request id.
- `coforge-installer upgrade --request-id <uuid> --version <latest|X.Y.Z> [--caller-pid <pid>]
  [--from-directory <dir>]`: one request. The id must satisfy `contract::is_request_id`; a replay of
  a finished id prints the same outcome. `--caller-pid` is the `upgrade` command that launched this
  installer, verified as its parent and never stopped.
- `--from-directory <dir>` (install and upgrade) takes the release from a local directory instead of
  the feed: `manifest.json`, `coforge-computer.gz` (this target's gzip), and `photon_rs_bg.wasm`, flat
  in one directory, the layout of the Computer's local package. It needs a concrete version, never
  `latest` (usage error, exit 1). Every check the feed path makes applies. It is for local builds
  (`scripts/`), not for users.
- `--allow-downgrade` (install and upgrade): lets the target be older than the
  active version. Without it, a target that orders below the active version by SemVer precedence
  (`version.rs`) is a failed receipt, `UPGRADE_DOWNGRADE_REFUSED`, exit 1, decided after the target
  resolves and before anything changes; a version that is not SemVer cannot be ordered and is refused
  the same way. The same or a newer version and a machine with nothing installed are never gated.
  The flag is not in the request record, so a replay ignores it. `recover` and rollback are not gated.
- `coforge-installer recover [--caller-pid <pid>]`: settles an unfinished upgrade (the journal).
  `--caller-pid` is the `coforge-computer recover` process that launched this installer and waits
  for it, verified and never stopped, as for `upgrade`.
- `coforge-installer repair [--version <v> | --channel main|latest] [--yes] [--allow-downgrade]
  [--json]`: under
  the machine lock, repairs the active installation without stopping the service. Healthy payloads
  only need activation links recreated; a damaged payload is quarantined and downloaded again
  through the manifest/checksum pipeline. An unneeded repair writes a held `REPAIR_NOT_NEEDED`
  receipt; successful repairs carry `outcome: "repaired"`, and request replays are supported.
- `coforge-installer status [--json]`: read-only, no lock. `--json` field names are documented in
  `src/status.rs`.
- `--version` prints the crate version.
Output: each stage line is `==> <stage>` on stdout, flushed as it happens (stderr in JSON mode). A succeeded install,
upgrade, or repair ends with `CoForge Computer <version> is active.`. A refusal or a failed
receipt's message goes to stderr as `coforge-installer: <message>`, or
`coforge-installer: <CODE>: <message>` when the receipt has an `errorCode`. A feed retry first
prints `coforge-installer: retrying <object> in <n>s
(attempt <k> of 3): <error>` to stderr. A feed request that failed 3 times ends its message with
`(3 attempts; proxy configured|proxy bypassed|no proxy)`; bypassed: `NO_PROXY` exempts the feed.
Exit status (`contract.rs`): 0 succeeded, 1 failed, 2 held (lock or request conflict), 3 unresolved
(run `coforge-computer recover`, or a rollback failed).
The release feed is compiled in (`src/compiled_feed.rs`): production defaults to
`https://releases.coforge.cn`; plain HTTP is allowed only for loopback end-to-end tests. No command
takes a feed.

## Toolchain

- `crates/installer/mise.toml` pins Rust (with rustfmt and clippy) plus cargo-deny, cargo-audit
  (`github:rustsec/rustsec`), and cargo-about. They stay out of root `mise.toml`, whose setup must
  never download Rust.
- Run every command from `crates/installer/`. mise merges the root config there too, so
  install only what you need: `mise install rust bun` (Bun runs the lock
  tests), or the four tools above for the supply-chain checks.
- Bumping a tool: change `crates/installer/mise.toml` (and `rust-version` in
  `crates/installer/Cargo.toml` for a Rust bump), then relock with
  `mise lock --platform linux-x64,macos-arm64`. Keep `lockfile_version = 1`:
  CI pins mise 2026.9.2, which cannot read revision 2, so never run
  `mise lock --upgrade` here. The core Rust backend locks no URL; rustup
  verifies it.
- The Cargo workspace is the repository root: `Cargo.toml` there lists the
  members under `crates/` (a new Rust crate goes in `crates/<name>`, never
  `packages/`), and holds the release profile and the one `Cargo.lock`; build
  output goes to the root `target/`.
- Change dependencies with `cargo add` / `cargo remove`, commit the root `Cargo.lock`,
  and pass `--locked` to every cargo command so CI never resolves a new graph.
  Add them with `default-features = false` and only the features used:
  rusqlite's default statement cache pulls in a Zlib-licensed hasher, and
  `deny.toml` allows only the licenses listed there.
- `cargo test` needs Bun (the root `mise.toml` pins it): the lock tests import
  `packages/daemon/src/platform/process-lock.ts` and fail, never skip, without
  it. Set `BUN` to use another binary. A Bun child that hangs is killed after
  `BUN_DEADLINE` and fails its test.
- There is no mise task for this crate, and it is not part of the root
  `mise run test` / `check` / `build`.

## Commands

```sh
mise exec -- cargo fmt --check
mise exec -- cargo clippy --locked --all-targets -- -D warnings
mise exec rust bun -- cargo test --locked     # Bun runs the Computer's lock
mise exec -- cargo build --locked --release     # ../../target/release/coforge-installer
mise exec -- cargo deny --locked check licenses bans sources advisories
mise exec -- cargo audit --deny warnings --file ../../Cargo.lock
mise exec -- cargo about generate --locked --fail --output-file THIRD_PARTY_NOTICES.txt about/notices.hbs
```

## CI

- Job `installer-crate` in `.github/workflows/ci.yml`. `scripts/ci/selection.ts`
  selects it for any `crates/installer/` path, the root `Cargo.toml` and
  `Cargo.lock`, `packages/daemon/src/platform/process-lock.ts` (the lock tests
  run it), and for the fail-open cases (CI, toolchain, unclassified paths), but
  not for workspace `package.json` changes or the Computer publication
  (`local`) track.
- One matrix entry per release target, each on its native runner:
  `darwin-arm64` and `darwin-x64` on `macos-latest` (x64 cross-compiled),
  `linux-x64` / `linux-arm64` on `ubuntu-24.04` / `ubuntu-24.04-arm` (musl,
  static), `windows-x64` / `windows-arm64` on `windows-latest` /
  `windows-11-arm` (MSVC).
- Every entry: clippy for its target, release build, size in the job summary,
  `--version` smoke run. Tests run on native entries only; darwin-x64 is built,
  signed, and run under Rosetta only when the runner has it.
- `linux-x64` alone also runs `cargo fmt --check`, cargo-deny, cargo-audit, and
  cargo-about, and uploads `THIRD_PARTY_NOTICES.txt` as the
  `coforge-installer-third-party-notices` artifact.
- Released by `release-installer-staging.yml`; see `docs/release/installer-feed.md`.

## Rules and gotchas

- The feed is read as `install.sh --prepare-directory` reads it: no redirects, `latest` ≤ 4096
  bytes, a manifest ≤ 1 MiB, every object capped at its recorded size (≤ 512 MiB) on the wire and
  expanded. Several gzip members, nothing after them. An installed version is verified and reused,
  never overwritten.
- A transfer that receives nothing for `fetch::IDLE_TIMEOUT` (60 s) fails; there is deliberately
  no limit on the whole download, which is legitimate on a slow link. Anything that changes the
  install root (`prepare_version`, `VersionStore::begin_staging`) takes `&MachineMutationLock` and
  checks it with `VersionStore::require_lock`, which refuses a lock on a different root: keep it
  that way for the next such function.
- Feed requests retry a transient failure (`feed::is_transient`: no connection, reset, timeout, cut
  short, a proxy refusing CONNECT, HTTP 408/429/5xx) afresh: 3 attempts, 2 s then 5 s apart on
  `Clock`. TLS, https_only, a bad URI or proxy URL fail at once. No Range resume: wire is hashed.
- `crates/installer/Cargo.toml` keeps `publish = false` and no `license` field; the repository
  has no license. `deny.toml` and `about.toml` ignore the private crate itself.
- `junction` (NTFS junctions, Windows only) is pinned `=1.2.0`. Its newer releases want
  `windows-sys` >= 0.59, but `ring` uses 0.52, and `multiple-versions = "deny"` rejects two.
  Move both together, never add a `deny.toml` `skip` for it.
- The license allow list in `deny.toml` is the gate. Adding a license to it is a
  licensing decision for Frank, not a CI fix. Keep `about.toml`'s `accepted`
  list in step with it.
- `install`, `upgrade`, and `recover` refuse to run inside `coforge-daemon.service` while it runs
  (the caller's cgroup names the unit): stopping the service would stop the installer. The refusal
  tells the person to run the command from a normal terminal, and changes nothing.
- `THIRD_PARTY_NOTICES.txt` is generated, never committed. The template must
  not print `source_path`: it is an absolute path on the build machine.
- No new lint, test, or advisory exemptions (`#[allow]`, `deny.toml` `ignore`
  or `skip`, `cargo audit --ignore`) without Frank's prior approval.
- `src/idle_timeout.rs` uses ureq's `unversioned` transport API (no semver guarantee), so
  ureq stays pinned in `Cargo.lock`. Bump it on purpose, starting there; the stall test in
  `src/fetch/tests.rs` catches an update that compiles but no longer bounds the wait.
- HTTPS verifies servers with the operating system's trust store, as the Computer does:
  ureq's `platform-verifier` feature (`rustls-platform-verifier`) with
  `RootCerts::PlatformVerifier`, on ureq's stable `rustls` feature (ring provider). The
  `rustls` feature also compiles `webpki-roots`, unused: that is expected, and it keeps the
  CDLA-Permissive-2.0 allowance in `deny.toml` matched. Never set the provider or root certs
  any other way (no `unversioned_rustls_crypto_provider`, no `native-tls`).
- Plain HTTP exists only as `fetch::Transport::LoopbackHttp`, chosen by `compiled_feed` for a
  loopback feed and by tests. The production agent is `Transport::Https`, with `https_only`.
- `schannel` (Windows, through `rustls-native-certs`) is pinned to 0.1.23 in `Cargo.lock`:
  0.1.24 and later need windows-sys 0.59 or 0.61, and `multiple-versions = "deny"` rejects a
  second windows-sys beside ring's 0.52. Move it with `junction` and windows-sys, never alone.
- `ureq` runs with default features off: its `gzip` feature would decode
  `Content-Encoding` transparently, and the manifest checksum covers the exact
  wire bytes.
- ring's build script compiles C. On Linux it needs `musl-gcc` (`musl-tools`)
  through `CC_<target>`; on `windows-11-arm` the runner's Visual Studio clang
  is enough.
- macOS 27 kills a binary whose signature is invalid. The arm64 linker signs
  its output; x86_64 output is unsigned, so CI ad-hoc signs it
  (`codesign --sign - --force`) and both must pass `codesign --verify --strict`.
