# Server modules

The module map of `src/server/`, split out of [`apps/web/AGENTS.md`](../../AGENTS.md#module-map). Each line names a directory under `src/` and its single responsibility. Update it before adding or reorganizing a module.

- `server/agent-migrations/` — moving an Agent and its workspace files to another Computer: state machine, step roles, fencing, stopping and starting the Agent around the transfer, the leases and cancels pushed to each Computer, and the daemons' HTTPS steps with presigned chunk URLs (`/api/daemon/agent-migrations`).
- `server/agent-app-configs/` — each Agent App's config for an Agent (the keys it overrode; defaults at revision 0 when unstored), the Agent's own read and revision-checked change of it (`coforge app config`), the daemon's snapshot, and pushing a change to a daemon that advertises `app-config:v1`.
- `server/agents/` — Agent lifecycle, control, sessions, a new Agent's introduction to its creator, display reduction,
  Activity (Computer lifecycle rows included), visibility, deletion, and the
  Agent HTTPS API, and platform assistants with private execution per member; `agent-message-reactions` dispatches comment reactions through AttachmentComments authority.
- `server/app-installation-data/` — what an installed app reads with its installation token (`/api/app-installations/<id>/{workspace,agents,channels,computers}`): the bearer check and RFC 6750 refusals, and the four projections (public fields only; private Agents, direct conversations and machine identity never leave the repository query).
- `server/app-agent-events/` — an installed app sending an event or notification to one Agent (Agent inbound, [docs](../../../../docs/app-agent-events/README.md)), behind the `app-agent-events` flag: the app's request and the grant that approves it, a person's approve, deny and revoke, accepting an event into the app's dedicated conversation with the Agent, and the Agent's `@app.<key>` target. Its HTTP side and token are in `server/authorization-server/` (`agent-inbound-endpoint`, `agent-inbound-tokens`).
- `server/app-agent-access/` — an Agent's access to the apps installed in its Workspace: listing (also the list an Agent's launch identity carries, `agentLaunchApps`), grant, revoke, approve and deny, the use-time rule (`decideAgentAccess`, applied by `resolveAgentAccess`), and the Agent's own use (`AgentAppUse`: `coforge app list|token`, the five-minute Agent token, the approval card), whose HTTP refusals are `server/agents/agent-app-refusals.server.ts`.
- `server/app-bots/` — an app's bot ([docs](../../../../docs/app-bot/README.md)): a Workspace owner or admin grants and revokes it per installation, the app's backend mints its key (the Agent API key format, stored by hash) and publishes its status line, and the bot's `/events` are read without taking it: the cursor handed back as `since` acknowledges. The Agent API's door for a bot key has deny-by-default capabilities (`app-bot-capabilities.server.ts`). The bot Agent has no Computer, so nothing launches it or pushes to a daemon. Only the Settings controls are behind the `app-bot` flag.
- `server/app-marketplace/` — Marketplace ([docs](../../../../docs/app-marketplace.md)): review of an app (an app's owners and admins request publication or removal and withdraw a request; a platform operator, `platform_operators`, decides, and an approved removal revokes the other Workspaces' installations), browsing the published apps of other Workspaces (also by an Agent with its own identity, read only), installing one with its approval (also the app a private share link names, through the same path) and uninstalling it, and an app owner's private share link (create for 1 to 365 days, regenerate, revoke; only the token's hash is stored). `marketplace-access.server.ts` is the one gate they share (member, then app-managing role).
- `server/app-notifications/` — the app notification outbox ([docs](../../../../docs/app-notifications.md)): `AppNotifications.record(tx, workspace, event)` writes an event as a pg-boss job in the caller's transaction, the worker fans it out behind the `app-notifications` flag, and `WebhookDelivery` signs it (Standard Webhooks) and POSTs it through `server/egress/` (webhook secrets are derived from `COFORGE_APP_WEBHOOK_KEY`, never stored). pg-boss (own `pgboss` schema) starts at server start (the SSR entry's first request), never inside a transaction, when the schema exists or the flag file defines the flag (and when a reloaded file first does), retrying a failed start with backoff. Domain code records a change by calling a per-area emitter (`workspace-events`, `channel-events`, `agent-events`, `computer-events`) inside its own transaction ([event data](../../../../docs/app-notifications/subscriptions.md#event-data)), never by building an event inline. The three Redis-lease presence events are the exception: the status caches report them (`presence-observer`) and `AppNotificationPresence` records them outside a transaction ([presence events](../../../../docs/app-notifications/presence.md)).
- `server/app-rate-limits/` — the per-minute request limits on the third-party app surface (`client_credentials` per app, installation reads per installation): a Redis fixed-window counter that fails open.
- `server/app-installation-setup/` — the page an app is set up on after installation, behind the `app-installation-setup` flag: what its Workspace declares (revision-bumped only when the page changes), each installation's status and the app's idempotent report of it, and the lookup of an installation in a Workspace; its HTTP side is in `server/authorization-server/` (`setup-endpoint`).
- `server/app-permissions/` — the data an app may read where it is installed, behind the `app-data-permissions` flag: what its Workspace declares for it (`workspace`, `agent`, `channel`, `computer`, read-only), each installation's revision-checked approval, and what follows (effective = approved ∩ declared; pending), and `AppEditorSave`, the editor's Save and registration of profile, groups and setup as one transaction.
- `server/apps/` — the app registry: the apps a Workspace registers (OIDC clients), their client secrets and logos; built-in Agent Apps are the SDK's `BUILT_IN_APPS`. An Agent that registered an app through a committed `app:register` card manages it as its owner Agent (`AppOwnerAgents`; `manager` is the one authorization for `AppAgentManagement`, which acts through the `...Managed...` operations of the registry, `AppShareLinks` and `AppPublishing`, which take the `ManagedApp` it returns; archived Agents are refused on every call), and the new client secret goes to that Agent's daemon privately (`AppRegistrationNotices`: capability `app-registration-notice:v1`, one publish over the daemon WSS, never stored or retried; an owner or admin-role Agent rotates a missed secret). One Agent's config of an App is `server/agent-app-configs/`.
- `server/artifacts/` — versioned artifacts (the `artifacts` experiment): `Artifacts` gates every operation on the experiment and on the home (a conversation's readers read, its active members write; a Workspace artifact is every member's; delete is the author's or an owner's or admin's), and saves immutable versions with a three-way merge (files by path, a document's text by line, settings by item; what does not merge answers `status: "conflict"`). Each new version is announced (`artifact.version.published.v1`) to its home's pages. The web page gets a document's text, never blobs. A save names only bytes its publisher uploaded or its artifact already uses (`artifact_blob_grants`). `artifact-blobs` stores the bytes by sha256 in the private file bucket under `workspaces/<id>/`, and its hourly sweep removes blobs no version has named for a day.
- `server/attachments/` — attachment upload sessions, claiming a sender's uploads for a new message, delivery, attachment comments whose authority follows the original conversation — except a file in a task discussion (`task_thread`), which takes it from the task's board channel or DM, since a task is read through its board, not its discussion seats; `agent-attachment-messages` adapts their scoped read/send targets; and the daily orphan-upload sweep (`attachment-orphan-sweep`: unclaimed Attachment rows past seven days, expired pending upload sessions, and a count of `verifying` sessions stuck over an hour). A comment notifies its uploader, prior commenters and @-mentioned source members in its own transaction (people a `reason`-carrying `pending_mention_actions` row, Agents a delivery), and `attachment-comment-notices` wakes them after commit (`activityChanged`, a delivery push addressed `attachment:<id>`). Comment migration owns read-only preflight and offline rehearsal, never application-startup migration.
  In the browser projection (`attachment-view.server.ts`): intrinsic image dimensions are an optional positive pair for inline raster images; storage keys never leave this view. The Agent message query omits these browser layout fields. `attachment-image-dimensions.server.ts` reads bounded image headers during upload; metadata failure leaves the upload usable.
- `server/auth/` — sign-in against Authing (password, verification-code and GitHub sign-in, sending the code, the password reset and the email-verification link), sessions, sign-out, username allocation, the first-sign-in name step, device auth, API keys, and auth guards. `authing-sign-in` is the sign-in every method shares (limits, Authing, session, token revocation); `password-reset` answers the same for a destination Authing does not know; `sign-in-rate-limits` holds the per-address, per-account-and-address and per-account attempt limits, the send limits and the per-user verification-link send limit, over `app-rate-limits`' Redis counter; `authing-webhook` (`/api/authing/webhook`) handles Authing's `user:email-verified` event, the only writer of `emailVerified`.
- `server/authorization-server/` — Login with CoForge: the OpenID Connect authorization server for third-party apps (issuer `<origin>/oidc`) with its own signing keyset: discovery, JWKS, the authorization endpoint (request checks, Workspace offering, remembered consent, authorization codes), the token and UserInfo endpoints (client authentication, PKCE, single-use redemption, JWT access and ID tokens, the claims each scope releases), Agents' app tokens (`mintAgentAccessToken`), installation tokens (`client_credentials`, behind `app-data-permissions` or `app-installation-setup`) and the installation setup API an app calls (`setup-endpoint`). The Computer device flow stays in `server/auth/`.
- `server/centrifugo/` — Centrifugo proxies, RPC receivers, and short-lived result caches.
- `server/computers/` — Computer registration, metadata, restart and upgrade
  operations, signing a Code Agent runtime in and out (`runtime-auth*`), runtime visibility, explicit model catalog refresh, and what the server remembers across a
  daemon's shutdown and return; `computer-connections.server.ts` is the narrow read of the Computers a member sees, with their connection state and optionally their runtimes, for screens that only pick or wait for one.
- `server/hosts/` — host-node enrollment, registration, heartbeat, the global online list, and container-computer jobs.
- `server/conversations/` — public channels, channel authority, stopping and resuming a channel's Agents, direct messages, history, message search, action cards, message forwards, reactions, tracked @mention delivery outcomes (`mention-deliveries`), the daily read-record retention sweep (`message-read-retention`), and conversation realtime.
- `server/db/` — the Prisma client, repositories (a DM's list preferences apart from its messages; the Agent attention rule in `agent-attention`), and the shared unique-violation check.
- `server/errors/` — public error mapping and request error handling.
- `server/feature-flags/` — whether a feature is on for a Workspace (`isFeatureEnabled`): the flag registry, and the flagd definition file the boot reads and installs as the OpenFeature provider (`COFORGE_FEATURE_FLAGS_FILE`).
- `server/egress/` — outbound HTTP to an address a third party chose (Web Push endpoints, app webhooks): resolve, require every address public, then send pinned to the checked address, no redirect (`OutboundEgress`).
- `server/files/` — file storage (per object, and bulk removal by keys or prefix), delivery, uploaded-image validation, and replacing a row's stored image (`stored-image-replacement`).
- `server/http/`, `server/install/`, `server/observability/` — public origin,
  response types and request timeouts, install scripts, tracing, and Server-Timing.
- `server/inbox/` — the Activity inbox read model and its Done and read-all writes.
- `server/integrations/` — GitHub connection, configuration, and webhooks.
- `server/notifications/` — Web Push and in-page notification delivery (its egress check is `server/egress/`), and a person's account notification settings (pause, quiet hours, preview, sound, a phone's wait while the computer is in use, the device list and test).

- `server/onboarding/` — `OnboardingWizard`: the first-sign-in wizard's state, assistant configuration (while it has never run) and completion (role saved, `onboardingPendingSince` cleared, assistant started).
- `server/pi-chat/` — User/Workspace-authorized native Pi commands (started, then their reply read by request id), scoped RPC reply chunks and private live feedback over the existing Daemon connection.
- `server/profiles/` — user avatars.
- `server/projects/` — project settings, images, and repository file download.
- `server/records/` — Workspace Records (see the last section).
- `server/release-catalog/` — each app release's notes (en, zh-CN): the self-contained release catalog, its PostgreSQL store, and its REST contract (`/api/release-catalog/v1`), split-ready for its own service.
- `server/reminders/` — cloud Agent Reminders.
- `server/runtime/` — process lifecycle of the built server: the boot-time configuration check (a Nitro plugin) and shutdown on SIGTERM/SIGINT (running the stops that timers, the database pool and Redis clients register with `onServerShutdown`, then exiting). Open Redis clients only through `openRedisClient` (`server/redis-client.server.ts`): it lifts Bun's default 20-retry reconnect limit, after which a client fails every command until the process restarts (`test/redis-client-reconnect.integration.ts`, Docker).
- `server/sweeps/` — `registerBackgroundSweeps`, the one call the Centrifugo RPC composition makes to start the periodic sweeps (Agent activity, app-notification presence) and to connect the presence observer to the status caches.
- `server/tasks/` — the message-backed TaskBoard, the shape a Task command must have, the Tasks page's overview reads, its Task view, history records, and notice wording.
- `server/usage-limits/` — provider usage-limit events: the Activity-observation hook that opens and merges them on quota reports, the sweep that closes them (reset passed, recovered, agents gone, aged out), the owner/admin-only list and seen/dismiss use cases, and the `usage.limit.changed.v1` push to owner/admin channels.
- `server/workspace-memory/` — memory profiles, grounded offers, task-requested or Memory-initiated four-role diagnosis (`memory-diagnosis-scope.server.ts` binds visible Task evidence), target-only Hint receipts and source ACL checks.
- `server/workspaces/` — Workspace catalog (name, icon and URL, with the former slugs that keep naming a Workspace), selection, enrollment, member roles, member directory, join links, admitting a member (`admitWorkspaceMember`, the one step a join link takes), who welcomes new members (`workspace-onboarding`, `member-welcome`), one submitted server connection per Workspace, deleting a Workspace, removing its memory first and its stored files after, and going out of a Workspace (leaving or deleting it) to the next one.

- Web-owned short-lived Redis state — the Agent and Computer status keys and the app-notification presence sorted set (`coforge:presence-expiry:v1`) — is rebuildable and non-authoritative (Frank approved 2026-10-23).

## Slow calls: start/read

Production closes a request that is idle for about ten seconds, and a Server Function that waits on a Computer or Daemon longer than about eight seconds must be split into two calls: `start` publishes and returns a request id (or a refusal as a value), and `read` returns `pending` or the settled outcome, re-checking access each time. The client polls through `poll-for-answer.ts` (`features/computers/AGENTS.md`).

- NO: one Server Function that publishes to a Computer and holds the request until the reply arrives.
- OK: `start` returns at once with a request id; the page polls `read` until it is no longer `pending`.

## Lock order

Two orders exist, for two different locks; do not mix them.

- Pins and Chat groups: `lockMemberPins` (the member's pin lock) before any conversation lock, then several conversation locks in id order. The other order deadlocks a menu pin against a drag (`server/conversations/`).
- Workspace deletion: conversation locks first, then the Workspace row (a key naming the Workspace), then the conversations again; every writer takes that order (`server/workspaces/`).
- A Task write's `withNotices` holds the one conversation lock (`server/tasks/`).
