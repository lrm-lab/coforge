# External Agents

Moved out of [`AGENTS.md`](AGENTS.md) to keep it under the size limit; the rules are unchanged.

- An external Agent (`Agent.hosting = "external"`) runs on any machine with no Computer or daemon; its runtime config is the inert `EXTERNAL_AGENT_RUNTIME_CONFIG`, and `external` is not a `RUNTIME_PROVIDER`. A person creates it (`createExternalAgent`, which also issues its first page credential and returns the key once). Keys are `sk_ext_` `ExternalAgentCredential` rows (at most 50 live per Agent, refusal `credential_limit`, no expiry, stored by hash), issued by the person who manages the Agent (its owner or a Workspace owner/admin, `external-agent-access.server.ts`, recorded as `approvedByUserId`) in two ways: `source` `app` is the page credential (`createExternalAgentPageCredential`, at most one live: issuing replaces it with reason `replaced`; no machine fields until used), `source` `device` is one per machine from `coforge agent login start` / `wait` (client `coforge-cli`). Neither touches the other.
- `authenticateExternalAgentRequest` runs before the bot door and claims every `sk_ext_` bearer; an `sk_agent_` bearer never reaches it. It works only on the routes `external-agent-capabilities.server.ts` lists: a new `/api/agent/v1` route is closed to external Agents until listed there, and a route that reads `principal.computerId` (always `NO_COMPUTER`) must not be listed. Refusals are 403 `unsupported_for_external_agents`; reminder schedule, update and snooze are 409 `reminders_unsupported_for_external_agents`.
- Presence: any authenticated request writes `lastUsedAt` at most every 30 seconds per credential, and that same throttled touch renews the Agent's online window in the display (`noteExternalSeen`): one Redis script per credential per 30 seconds, started after the touch without holding the request, nothing on the requests in between, and a publication only when what the dot shows changed. Never add a per-request write. `externalSetup` (`waiting`, `online` within 2 minutes of a live credential's use, `offline`, `disconnected`) still comes from `external-agent-presence.server.ts` for the setup panel and the roster's channel reads; the dot is the display of scope `computerId: ""`, read with the managed Agents' displays through `agentDisplayScope` and never computed on read. Every path that can end the last live credential (self logout, revoke, page replace, Stop, delete) calls `syncExternalPresenceBestEffort` after its write, which overwrites the window from the database, so another live credential keeps the Agent online.
- External display scripts (`agent-display-lua-external.ts`) keep external Agents out of the busy-lease set the sweep probes a Daemon for, so `busyScopes` never lists one; the extra-Agents read asks for every visible external Agent itself. A reported `offline` holds against later presence renewals until a newer report or the window lapsing; a reported `error` never sets a stop reason, because that opens the retry and reset controls external Agents refuse. Working and thinking last until the next report or the window ends (the client's refresh adds about 6 seconds before it drops a busy dot).
- `POST /api/agent/v1/activity` (`external-agent-activity*.server.ts`) validates the whole request before any side effect, then claims event ids (24-hour Redis keys, released if the write fails so the retry is not skipped), applies only the newest status report, or else the newest hook guess, to the display (at most one script per request), writes hook rows (`launchId` `external:<eventId>`, `computerId` null: the only Activity rows without a Computer) and publishes. `Agent.externalStatusReportedAt` is the permanent flag that ends hook-derived dots; set it only for a status report, never for a subagent or legacy-outcome event.
- Like a bot, an external Agent reads `/events` through `AppBotInbox`, and `isInboxPolled` keeps its messages and mentions pending instead of pushing or launching. It owns no Reminder: schedule, update and snooze are refused. Stop revokes every key (`agent_stopped`), as deletion does (`agent_deleted`); Restart and Reset are refused with `agent-external-no-runtime`.
- Key events are logged as one-line JSON (`external_agent.*`), never with key material.
- Wake paths carry hints, never bodies, and never read or acknowledge anything. `external-wake-hints.server.ts` groups `unreadAgentMessagesFragment` (the state `/events` reads) per reply target in one statement; the stream and the webhook both build their hints from it.
- `announceMessage` starts `noticeExternalInbox` after every committed message without waiting for it, so the realtime publish never queues behind it: one statement finds the live external Agents with a seat in the conversation (or a mention from outside it), wakes their streams through `externalInboxSignal` (`cacheInvalidation`: in-process, plus Redis across instances) and enqueues one notice for those with a ready push webhook. A wake path it misses is covered by each stream's safety re-query (`WAKE_SAFETY_REFRESH_MS`, 3 minutes; the 25-second heartbeat revalidates the credential, which counts as being seen, but does not query hints); a new write path needs no change unless it posts without `announceMessage`.
- A push webhook (`external_agent_push_webhooks`) runs on the app-notification pg-boss instance, in its own queue (`short` policy keyed by Agent, so rapid writes coalesce). The job carries only the Agent id; hints are built at attempt time. The worker owns every retry delay and reschedules itself, checks the Agent at each attempt, and writes outcomes fenced by `revision`. While `endpoint_rejected` the worker probes the endpoint with a `targets: []` notice (`external-push-recovery.server.ts` holds the schedule): a delayed job keyed `<agentId>:probe` in the same queue, so a probe never replaces a notice job. `nextProbeAt` on the row is the truth: a probe job that fires early or for a row no longer rejected does nothing, and `startAppNotificationQueue` re-enqueues every pending probe at start (the singleton key drops a duplicate), so a lost job or a restart does not end the chain. A 2xx probe re-enables push and enqueues an ordinary notice. The secret is sealed with the Agent credential encryption key (`COFORGE_AGENT_CREDENTIAL_ENCRYPTION_KEY`), bound to the Agent id. `startAppNotificationQueueIfNeeded` also starts the queue when a registration exists, and `PUT` answers 503 when it cannot.
